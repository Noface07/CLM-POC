Salesforce By Hand

Everything the deploy command created, done through the Salesforce interface instead: two objects, forty fields, the formula that gates contract initiation, the demo records, and the app to see them in. Every value here is read out of the metadata that is actually deployed in your org, so the two cannot drift.

Read this as reference, not as a to-do list.

Your org already has all of it. This exists for the time you need to rebuild in an org where you cannot run the CLI — a client’s sandbox, a locked-down environment, or a screen-share where somebody wants to watch it being made. Budget two to three hours; the field creation is the bulk of it.

Finding anything in Setup

The single thing that makes Salesforce navigable. Learn this and the rest is forms.

The gear icon at the top-right opens a short menu — Setup, Data Cloud Setup, Developer Console. That menu is not Setup. Click Setup in it and a new tab opens.

Inside Setup, the only navigation that matters is the Quick Find box at the top of the left-hand column. Almost nothing is reachable by browsing the tree; you type what you want and click the result. Every instruction below is written as Setup → Quick Find: “…”, meaning type that phrase into the box.

Two rules the form will not warn you about.

A required lookup cannot be Set Null on delete. When you tick Required on Account, choose Don't allow deletion… for the delete behaviour, or the save is rejected.

Currency fields need multi-currency for a currency picker. A fresh org has one currency, which is fine — that is why the CLM sends Currency_Code__c as plain text rather than relying on CurrencyIsoCode.

the important one5 min

The Create Contract formula

This is the gate. It only offers the link when all four prerequisites are met, and it recomputes every time the page is drawn — nothing is scheduled or cached.

  1. Object Manager → Supplier Onboarding → Fields & Relationships → New
  2. Type Formula → Next
  3. Field Label Create Contract, Field Name CLM_Workspace_URL, Formula Return Type Text → Next
  4. Click Advanced Formula and paste:
IF(
  AND(
    ISPICKVAL(Onboarding_Status__c, "Approved - Ready to Contract"),
    Qualification_Complete__c,
    Insurance_Verified__c,
    Bank_Verified__c,
    Sanctions_Cleared__c
  ),
  HYPERLINK("http://localhost:5173/#sf?onb=" & Id & "&acct=" & Account__c,
            "Create Contract", "_blank"),
  "Onboarding incomplete"
)
  1. Check Syntax. It should say no errors.
  2. Next, Next, Save.
Change the URL when you deploy the CLM.

http://localhost:5173 is your dev server. For a hosted demo, edit this formula and swap it for the deployed address. Both ids must survive the change: onb is the record the CLM writes status back to, acct is the supplier a contract belongs to.

4
permission sets10 min

Grant yourself access

Creating a field does not give anyone access to it, including you. Skip this and records look empty for no visible reason.

  1. Setup → Quick Find: “Permission Sets” → New
  2. Label CLM Integration, API Name CLM_Integration, License --None-- → Save
    • Leaving the licence as None is deliberate: a permission set tied to a licence can only be assigned to users who hold it.
  3. Click Object Settings. For Supplier Onboarding and CLM Contracts, in each: Edit → tick every Object Permission (Read, Create, Edit, Delete, View All, Modify All) → tick Read and Edit on every field → Save.
    • Create Contract is a formula — it offers Read only. That is correct.
    • Account on Supplier Onboarding is required, so it shows no checkboxes at all. Also correct: a field you must fill in cannot be hidden from anyone.
  4. Back on the permission set, click Assigned Users → Add Assignments → tick yourself → Assign.

Build the app, so you can find any of it

Without this the objects exist but are only reachable through the App Launcher, which caches badly and opens them as temporary tabs that vanish. A dedicated app is additive and cannot disturb anything already in the org.

  1. Setup → Quick Find: “App Manager” → New Lightning App (top right)
  2. App Name FM Contracting, Developer Name FM_Contracting → Next
  3. Appearance and Utility Items: skip both with Next.
  4. Navigation Items: move Home, Accounts, Supplier Onboarding and CLM Contracts into Selected → Next
  5. User Profiles: add System Administrator → Save & Finish
  6. Open the App Launcher (nine dots, top-left) and pick FM Contracting.
If the app does not appear, log out and back in.

App visibility is cached for the session. A hard refresh often is not enough; logging out reliably rebuilds the navigation.

Add an “All” list view

A new object ships with one list view: Recently Viewed, which shows records you have personally opened. Records created by a script or an API call are not in it, so a correctly populated object looks identical to an empty one. This is the single most confusing thing about a fresh custom object.

  1. Open the object’s tab, then the gear icon above the list → New
  2. List Name All, and under Who sees this list view pick All users can see this list view → Save
  3. In the filter panel that opens, set Filter by Owner to All supplier onboarding → Save
  4. Click Select Fields to Display and add the columns worth seeing: Onboarding Status, Service Category, Anticipated Contract Value, CLM Contract Status.
  5. Repeat for CLM Contracts: Contract Reference, Supplier, Contract Status, Current Version, PO Eligibility.

connect the clm5 min

Get a token without the CLI

  1. Gear icon → Developer Console (a new window opens)
  2. Menu Debug → Open Execute Anonymous Window
  3. Paste System.debug(UserInfo.getSessionId());, tick Open Log, click Execute
  4. In the log, tick Debug Only at the bottom. The long string starting 00D is your token.
  5. Your instance URL is in the browser address bar, with lightning.force.com replaced by my.salesforce.com.
This token dies with the session.

Log out, or leave it a few hours, and the CLM will report a 401. Take a fresh one the same way. For anything longer-lived you need a Connected App with OAuth, which is a different exercise.

8b
app manager10 min, then a 10 min wait

Create the Connected App, so the CLM can sign in properly

A pasted token dies with the session. A Connected App lets the CLM sign in through the org’s own login page and come back with a refresh token, so it renews itself and nobody pastes anything again. This is the OAuth version.

  1. Setup → Quick Find: “App Manager” → New Connected App (top right)
    • If the page offers Create a Connected App vs Create an External Client App, choose Connected App.
  2. Basic Information: Connected App Name FM CLM Demo, API Name FM_CLM_Demo, Contact Email — yours.
  3. Tick Enable OAuth Settings. The section expands.
  4. Callback URL — one per line: 
    http://localhost:5173/
https://noface07.github.io/CLM-POC/
    • The trailing slash matters. Salesforce matches the callback exactly, and the CLM sends its root with the slash.
  5. Selected OAuth Scopes — move these three across: Manage user data via APIs (api), Perform requests at any time (refresh_token, offline_access), Access unique user identifiers (openid).
  6. Tick Require Proof Key for Code Exchange (PKCE).
  7. Untick Require Secret for Web Server Flow and untick Require Secret for Refresh Token Flow.
    • A browser cannot keep a secret, so a client that needs one is a client that has already leaked it. PKCE is the replacement. Leaving either ticked makes the sign-in fail with invalid_client.
  8. Save, then Continue. Salesforce warns it can take up to ten minutes to take effect. It means it.
  9. On the app’s page, click Manage Consumer Details. Salesforce emails you a verification code; enter it. Copy the Consumer Key (the long string starting 3MVG9). You do not need the secret.
  10. Back on the app’s page, Manage → Edit Policies → set Refresh Token Policy to Refresh token is valid until revoked → Save.
The ten minutes are real.

Clicking Connect before the app has propagated gives error=invalid_client_id on the Salesforce login page. It is not a configuration mistake. Wait, then try again.

in the clm project3 min

Tell the dev server where your org is

Before the panel can do anything, the dev server has to know the address to forward to. This is one file and one restart, and it is where most people get stuck — because nothing warns you when it is missing.

  1. In the project root — the folder with package.json, not the salesforce folder — create a file named exactly .env
  2. Put two lines in it — your instance URL from step 8, and the consumer key from step 8b: 
    VITE_SALESFORCE_URL=https://yourorg.my.salesforce.com
VITE_SF_CLIENT_ID=3MVG9…
    • There is a .env.example in the project showing the shape. Neither value is a secret.
  3. Stop the dev server and start it again. Ctrl+C in the terminal running npm run dev, then npm run dev.
Vite reads .env once, at startup.

Editing it while the server runs changes nothing, and the failure is silent: the panel will keep calling login.salesforce.com, which answers, but is not your org. If Test connection gives you something strange after a correct token, this is almost always why.

Instance URL confuses everyone once.

It looks wrong to leave /salesforce in a field labelled Instance URL. The browser calls /salesforce/services/data/v60.0/… on your own dev server; Vite rewrites that to your org and forwards it. That indirection is what avoids the browser’s cross-origin rules in development.

Drive the round trip

Two browser windows side by side: Salesforce on one, the CLM on the other.

  1. In Salesforce, open FM Contracting → Supplier Onboarding → All, and open the Meridian record.
  2. Click Create Contract. The CLM opens on the Salesforce panel, says it is reading the record, then lands in the draft studio with the supplier, company number, value, site and payment terms already filled in from the org.
  3. Click Create draft, then run the contract through: send to supplier, return a redline from Supplier view, run change intelligence, decide the exceptions, sign both parties.
  4. Back in Salesforce, open the CLM Contracts tab and refresh. There is a record with the contract reference, the status climbing the picklist, the version moving, and PO Eligibility ticking to true only once it is Executed.
  5. Open the Meridian onboarding record again: CLM Contract Id and CLM Contract Status are now filled in. The journey that offered the button shows what came of it.
Try the negative case too.

Open Ferrow in Salesforce and copy its Create Contract URL by hand — or untick a box on Meridian after loading the page, then click the stale link. The CLM refuses and names the missing prerequisites, because it re-runs the gate on arrival rather than trusting the link. A link that was valid when the page was drawn is not the same as a supplier who is still eligible.

Where every setting comes from

Each field on the connection panel: what it does, and the clicks that produce its value. For the day the .env is lost, the org is a different one, or somebody asks.

A

Consumer key

What it does. Identifies the Connected App. When the browser arrives at the login page carrying this key, Salesforce looks up FM CLM Demo and checks the callback URL and scopes against what that app is allowed. It is not a secret: a PKCE public client carries it in the page by design, and knowing it lets nobody in without also passing the org’s login.

  1. Setup → Quick Find: “App Manager”
  2. Find the row FM CLM Demo. Its type column says Connected.
  3. Click the ▾ at the far right of that row → View
  4. Under API (Enable OAuth Settings), click Manage Consumer Details
  5. Salesforce emails a verification code to your login address. Enter it.
  6. Copy Consumer Key — the long string beginning 3MVG9. Ignore Consumer Secret; the CLM does not use one.
The verification email is the slow part.

It can take a minute and sometimes lands in spam. If you have the CLI, the same key comes back without any email: sf project retrieve start --metadata ConnectedApp:FM_CLM_Demo, then read <consumerKey> from the file it writes.

B

Login URL

What it does. Your org’s My Domain. The browser is sent here to sign in and to the “Allow access?” page. Because it is a redirect rather than an API call, it cannot go through the dev proxy — it has to be the real address. It is also what VITE_SALESFORCE_URL is set to in .env.

  1. Setup → Quick Find: “My Domain”
  2. Under My Domain Details, read Current My Domain URL. It looks like orgfarm-6a278698bc-dev-ed.develop.my.salesforce.com.
  3. Put https:// in front of it. No trailing slash.
Or read it off the address bar.

Any Salesforce page’s URL is the same host with lightning.force.com at the end. Swap that for my.salesforce.com and you have it. The .develop. part stays.

C

Instance URL

What it does. Where API calls go — the supplier query, the token exchange, the status writeback. Not the same thing as the Login URL, even though from a deployed site they hold the same value.

  • From npm run dev: leave it as /salesforce. That is a path on your own dev server. Vite sees it, strips the prefix, and forwards the call to the address in .env. The browser never talks to Salesforce directly, so its cross-origin rules never apply.
  • From a deployed site: there is no Vite. Set it to the Login URL, and allowlist your site’s origin at Setup → Quick Find: “CORS” → New, e.g. https://noface07.github.io.
D

API version

What it does. Which release of the REST API the CLM speaks. Salesforce ships three a year and keeps old ones working for many years, so the choice rarely matters: everything the CLM does — SOQL, upsert by external id, the OAuth endpoints — has worked identically since long before v60.0. Newer versions add things; they do not remove these.

  1. While logged in, open a new browser tab at https://<your Login URL>/services/data/
  2. Salesforce answers with a list of every version the org supports. The last entry is the newest, e.g. "version": "65.0".
  3. Use any of them as vNN.0. v60.0 is a safe default for any org created after 2024.
When you would change it.

Only if a call fails with “The requested resource does not exist” on a fresh org that is somehow older than v60 — which a Developer Edition or trial created today will not be.

E

Supplier object

What it does. The API name of the table the supplier list is read from and the status pointer is written back to. It is a setting because blueprint §14 says the org’s object model is still to be validated; if onboarding ends up living somewhere else, this changes and the code does not.

  1. Setup → Quick Find: “Object Manager” → click Supplier Onboarding
  2. On the object’s Details page, read API Name: Supplier_Onboarding__c. The label is what a person sees; the API name is what code sends.
F

Status / ID fields written back

What they do. On every lifecycle transition the CLM writes two values onto the onboarding record: the contract’s reference and its current status. These are the API names of those two fields. The fuller record — version, signature, PO eligibility — goes to CLM_Contract__c and is not configurable, because its shape is the CLM’s.

  1. Object Manager → Supplier Onboarding → Fields & Relationships
  2. Find CLM Contract Status and CLM Contract Id. The Field Name column shows the API names: CLM_Contract_Status__c and CLM_Contract_Id__c.
G

Authentication

What it does. How the CLM proves who it is on every call. This one is a choice, not a value from Salesforce.

  • Sign in with Salesforce — OAuth through the Connected App. The org issues an access token and a refresh token; when the access token expires the CLM swaps the refresh token for a new one and retries, so a 401 is never seen. The connection survives a reload and is revoked at the org by Disconnect.
  • Paste a session token — the step-8 route. Fast, needs no Connected App, dies with the session. Fine for building; the other one is for demoing.
What neither option changes.

The access token lives in the browser, readable by anything on the page. OAuth removes the need for a client secret; it does not move the token to a server. Enough to prove the integration against an org you own; in production the call and the credential belong on a server.

Running from a deployed URL rather than dev

In development the Vite proxy means the browser never talks to Salesforce directly. On a deployed site there is no proxy, and Salesforce refuses calls from an origin it does not know. Two things then become necessary:

  1. Setup → Quick Find: “CORS” → New → add your site’s origin, e.g. https://noface07.github.io
  2. Set the CLM’s Instance URL to your real org address instead of /salesforce, since there is no proxy to hand it to.
  3. Update the Create Contract formula (step 3) to point at the deployed address.
The caveat the panel states, restated.

A token in a browser tab is readable by anything running on that page, and Salesforce’s CORS allowlist does not change that. This shape is enough to prove the integration against your own org and is not enough to ship: in production the call and the credential belong on a server. That is worth saying out loud when you demo it, rather than being asked.
