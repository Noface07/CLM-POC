Six words you will see constantly

Salesforce has its own vocabulary for ordinary things. This is all of it you need.

WordWhat it actually means
OrgYour own private copy of Salesforce. Yours will be free and permanent. “Org” is short for organisation.
ObjectA table. Account is a built-in one. Supplier_Onboarding__c is one we are adding — the __c suffix just means “custom”.
FieldA column on that table. Also gets __c when custom.
RecordA row. One supplier is one Account record.
API nameThe name code uses, e.g. Contract_Value__c. Different from the label a person sees (“Contract Value”). Our code depends on the API names, so do not change them.
SetupThe admin area. Always the gear icon in the top-right of any Salesforce page.

1
in a browser10 min, mostly waiting for email

Create your free Salesforce org

  1. Go to developer.salesforce.com/signup
  2. Fill the form. First name, last name, a real email you can open, job role and country — anything sensible.
  3. Username is the one that confuses everybody. It looks like an email but is not one; it just has to be globally unique across all of Salesforce and no mail is ever sent to it. Use something like yuvraj@clmpoc.demo. Write it down — this is what you log in with.
  4. Submit. Check the email you gave for a message titled roughly “Welcome to Salesforce: Verify your account”. It can take a couple of minutes.
  5. Click the link, set a password, pick a security question. You land on the Salesforce home page.
Note your org address.

Look at the browser address bar. It will be something like https://orgfarm-a1b2c3-dev-ed.develop.lightning.force.com. The part you will need later is the same host with my.salesforce.com instead of lightning.force.com. Do not worry about copying it precisely now — step 3 prints it for you.

2
in your terminal2 min

Install the Salesforce command-line tool

This is what lets you push files into the org instead of clicking. You already have Node and npm, so it is one command.

npm install --global @salesforce/cli

# check it worked -- you should see a version number
sf --version
If sf is “not recognised” afterwards

Close your terminal and open a new one. Windows only picks up newly installed global commands in a fresh terminal. If it still fails, run npm config get prefix — that folder needs to be on your PATH.

in your terminal1 min

Connect the tool to your org

cd C:\Users\yuvra\Downloads\Demo-5\clm-demo_4\clm-demo\salesforce

sf org login web --alias clmdemo --set-default
  1. A browser window opens on the Salesforce login page.
  2. Log in with the username from step 1 (the fake-email one) and your password.
  3. A page asks you to Allow access. Click it.
  4. The browser says you can close it. Back in the terminal you will see Successfully authorized … with org ID …

--alias clmdemo just gives the connection a short name so you do not retype the username every time. Everything below uses it.

Deploy the objects and fields

Still inside the salesforce folder. This is the command that replaces the afternoon of clicking.

sf project deploy start --target-org clmdemo

Deploying v62.0 metadata to yuvraj@clmpoc.demo …
Status: Succeeded | ████████████████████ | 48/48 Components

That created two objects, forty fields, two page layouts, two tabs and a permission set. If it says Succeeded, the Salesforce half of the data model is done.

If it fails, read the first error only.

Deploy errors cascade — one bad field produces ten complaints. Fix the first, run again. The likely ones are in the troubleshooting table at the bottom.

5
permissions30 seconds

Give yourself access to what you just made

Salesforce does not automatically grant access to new fields, even to the person who created them. The permission set in the deploy grants all of it; you just have to switch it on for yourself.

sf org assign permset --name CLM_Integration --target-org clmdemo
Skip this and everything looks broken in a confusing way.

Records exist but fields appear blank, and the CLM’s queries return rows with missing values rather than an error. If something reads empty later, come back and check this ran.

7
in the browser5 min — worth doing

Go and look at what you built

Do not skip this. You need to know your way around these screens for the demo, and it confirms steps 4–6 really worked.

  1. Open your org: sf org open --target-org clmdemo — or just use the browser tab you already have.
  2. Click the App Launcher: the grid of nine dots at the top-left.
  3. Type Supplier Onboarding in the search box and click it.
  4. You land on a list view. If it says Recently Viewed and looks empty, change the dropdown above the list to All. Your three records appear.
  5. Click the Meridian one. You are looking at the record page: all twenty fields, and at the bottom a field labelled Create Contract showing a blue link.
  6. Now open the Ferrow record. Same field, but it reads Onboarding incomplete — because two of its checkboxes are unticked. That is the §6.1 gate working.
Try this, it makes the gate obvious.

On the Ferrow record, click Edit, tick Insurance Verified and Sanctions Cleared, set Onboarding Status to Approved - Ready to Contract, and Save. The Create Contract link appears immediately. Untick one and it vanishes again. Nothing is scheduled or recalculated — a formula field is computed every time the page is drawn.

8
in your terminal1 min

Get the two values the CLM needs

The deploy in step 4 also created a Connected App called FM CLM Demo: the thing that lets the CLM sign in through the org’s own login page and come back with a refresh token, so nobody pastes anything and a 401 is handled rather than seen. The CLM needs the org’s address and the app’s consumer key.

# 1. the org's address
sf org display --target-org clmdemo --verbose
  Instance Url   https://orgfarm-a1b2c3-dev-ed.develop.my.salesforce.com

# 2. the consumer key: Salesforce generated it, so read it back out of the org.
#    (The UI route -- Manage Consumer Details -- emails you a verification code first.)
sf project retrieve start --metadata ConnectedApp:FM_CLM_Demo --target-org clmdemo
grep consumerKey force-app/main/default/connectedApps/FM_CLM_Demo.connectedApp-meta.xml
  <consumerKey>3MVG9HtWXcDG…</consumerKey>
Neither value is a secret.

The consumer key belongs to a public client: the app uses PKCE instead of a client secret, because a browser cannot keep a secret and pretending otherwise is worse than not having one. The key is in the page by design.

Give the Connected App ten minutes.

Salesforce takes up to ten minutes after creation before a new app can sign anyone in. Until then the login page answers invalid_client_id. It is not a configuration mistake; wait and try again.

9
in the CLM5 min

Point the CLM at your org

  1. In the project root (not the salesforce folder), create a file called .env with both values from step 8 (there is a .env.example showing the shape): 
    VITE_SALESFORCE_URL=https://orgfarm-a1b2c3-dev-ed.develop.my.salesforce.com
VITE_SF_CLIENT_ID=3MVG9HtWXcDG…
  2. Stop and restart npm run dev. Vite only reads .env at startup, so a running server will ignore it.
  3. In the CLM, click Salesforce ↗ in the top bar, then open Integration settings.
  4. Set Mode to live.
  5. Leave Instance URL as /salesforce. That is not a mistake — it is the dev-server proxy path, and the proxy is what forwards your calls to the address in .env.
  6. Authentication should already read Sign in with Salesforce, with the consumer key and login URL pre-filled from .env. Click Connect to Salesforce.
  7. The org’s login page opens. Sign in. A page asks whether to allow FM CLM Demo access: Allow. You are sent back to the CLM, which now shows Connected and your name.
  8. Supplier object already reads Supplier_Onboarding__c; leave it.
  9. Click Test connection. Success looks like “Connected. Daily API requests: 14,987 of 15,000 remaining.”
If you would rather not sign in.

Switch Authentication to Paste a session token and use the Access Token from sf org display --verbose. It works identically and expires within hours; the CLM reports a 401 when it does, and you paste a fresh one. Fine for building. The OAuth route is for demoing.

The CLM code is done.

The live query now reads all twenty onboarding fields and reaches the supplier through Account__r, the four checkboxes drive the eligibility gate, the #sf link opens a pre-filled draft, and every status change writes a CLM_Contract__c record. All of it is verified against a stubbed org, so the only thing your token adds is the real network.

Once Test connection succeeds, the supplier list shows your three real records with Ferrow marked blocked — that is the eligibility gate reading live checkboxes. Then go back to Salesforce, open the Meridian onboarding record, and click Create Contract. The CLM opens with the draft studio pre-filled from the org.
